# 新传感器的组织方式

## 一个传感器一个目录

后续项目放在 `sensors/<传感器英文名>/`，例如 `temperature-humidity` 或 `ultrasonic`。这些只是命名示例，尚未建立对应库。

每个传感器拥有自己的 config.json、arduinoC、assets、examples、tests、tools、README.md 和验证记录。Mind+ 规定的 config.json、arduinoC/main.ts、_menus、_images、libraries 等名称保持不变。

每个用户库的 `config.json.id` 必须唯一，且与 main.ts 的 namespace 一致。新传感器不能沿用编码器的 id。author 与 id 是库的身份标识，发布后尽量保持稳定；正常更新修改 version。

## 文件职责

- `arduinoC/`：Mind+ 真正读取的代码和素材。
- `assets/`：原始照片、插画原图或设计提示词；只保留与该传感器有关的资料。
- `examples/MindPlus/`：可编辑的 .mp 或 .sb3 积木项目，以软件实际保存格式为准。
- `examples/Uno/`、`examples/Mpython/`：仅限本地的 Arduino 验证草图，已加入 Git 忽略规则；不上传，也不进入发布 ZIP。公开示例仅提供 Mind+ `.mp` 项目。
- `tests/`：有价值的自动验证；编译结果和日志放 .verification，避免混入源码。
- `README.md`：接线、适用硬件、积木搭法、导入步骤。
- `VALIDATION.md`：分别记录生成器检查、编译、软件导入和实物测试，避免混淆。
- `releases/<传感器英文名>/`：当前可发送的 .mpext、项目文件、源码 ZIP 和说明。
- `releases/<传感器英文名>/archive/`：旧版本或目录调整前的历史包。

## 复用什么

编码器库可作为 Mind+ 1.x 项目结构参考。新传感器需要按接口和通信协议重新实现驱动，不直接沿用 A/B 编码器逻辑。公共代码只有在多个传感器确实使用时再提取。

保留每个库的独立性：整个传感器目录解压到另一台电脑后仍能从 config.json 导入，不依赖其他传感器目录。封面使用 600×372 的 featured.png。

## 打包约定

每个传感器的 `tools/package.py` 接受 `--output-dir` 参数；默认可输出到自身 dist 文件夹，以支持单独使用。工作区 `tools/package.py <传感器英文名>` 将输出统一放到 releases，并复制示例与分享说明。

从任意目录调用脚本时，脚本依据自身文件位置寻找源码，不依赖当前工作目录。示例副本在打包时更新，平时只编辑源码目录中的原始示例。开发检查从传感器根目录执行，或在检查脚本里显式确定项目路径。

## 开始下一个传感器时提供的信息

告诉我传感器名称或型号、实物/引脚标识、协议资料，以及要支持的主控和期望积木功能。我会在新的 sensors 子目录中开发，并使用同样的发布结构。
